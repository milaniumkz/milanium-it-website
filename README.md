# MILANIUM

Подготовка размещения сайта. Исходники и домен будут добавлены после получения. Этот комплект ничего не запускает и не меняет на сервере. Автоматического деплоя нет.

## После получения архива и домена

1. Распаковать исходники **локально** и проверить стек, зависимости, состав архива и историю на наличие ключей, `.env`, внутренних адресов и клиентских данных. Не публиковать необработанный архив. Определить, что требуется: статическая сборка, серверное приложение или функции платформы Sites. Функции платформы и серверные интеграции проверяются на переносимость отдельно. Собрать образ вне общего сервера, проверить в тестовой среде и зафиксировать digest.
2. Перед первой установкой на целевом хосте проверить без изменений: используемый прокси, версию контейнерного движка, свободное место/память, действующие слушатели и наличие проекта `milanium-web`. Снять короткий исходный результат безопасных GET-проверок MTaxi и MBusiness. Если есть коллизия, ресурсы на пределе, Docker Compose не установлен или прокси не может обращаться с хоста к loopback, **остановиться** и адаптировать план. Не устанавливать Docker и не менять общую сеть для запуска этого шаблона.
3. Для совместимого сервера с Docker Compose использовать `deploy/compose.yaml`: отдельный проект, собственная сеть, хостовый порт только на `127.0.0.1`, без общих томов, баз данных и привилегий. Образ должен запускаться пользователем 10001, работать с read-only root filesystem и слушать на `0.0.0.0` **внутри** контейнера на порту ≥1024. Параметры ресурсов проверить нагрузкой до запуска; это границы по умолчанию, а не гарантия ёмкости. Проверить недоступность порта извне; на старых версиях Docker одна привязка к loopback может не обеспечивать ожидаемой изоляции. Никаких портов 80/443 для контейнера.
4. Заполнить локальный `deploy/.env` по примеру. Для доступа использовать отдельный утверждённый способ выпуска, без общих ключей и токенов. Никогда не добавлять доступ к хосту в workflow, исполняющий код публичного PR.
5. После проверки образа и одобрения первого запуска:

   ```sh
   unset MILANIUM_IMAGE MILANIUM_HOST_PORT MILANIUM_CONTAINER_PORT
   sh deploy/plan.sh
   docker compose --env-file deploy/.env -p milanium-web -f deploy/compose.yaml pull web
   docker compose --env-file deploy/.env -p milanium-web -f deploy/compose.yaml up -d --no-deps web
   ```

   Запускать команды только последовательно, прекращая на ошибке. Проверить страницу сайта прямым GET по loopback и журналы только своего контейнера; форма или интеграции тестируются на тестовых данных. Если сайт ещё не завязан на домен, внешний трафик при этом не переключается.
6. Только после успешной проверки подготовить отдельную конфигурацию маршрута для точного домена MILANIUM, без `default_server`, wildcard, правок существующих виртуальных хостов и изменения их сертификатов. Проверить DNS и сертификат, валидировать конфигурацию прокси до применения; согласовать безопасное применение только нового маршрута. Проверить HTTPS, главную и переходы. Повторить те же GET-проверки MTaxi и MBusiness. При ухудшении сначала снять **только** новый маршрут и остановить **только** MILANIUM; не перезапускать соседние процессы.

## Откат

Зафиксировать предыдущий рабочий digest перед каждым выпуском. Если сбой только в новой версии, вернуть прежний digest в локальном `deploy/.env`, снять переменные MILANIUM_* из оболочки и повторить проверки и `up -d --no-deps web` только этого проекта. На первом выпуске отключить новый маршрут и остановить сервис командой `docker compose --env-file deploy/.env -p milanium-web -f deploy/compose.yaml stop web`. Не применять общие `prune`, `down -v`, перезапуск Docker или очистку диска соседних приложений. При необходимости отдельного хранилища или БД проектировать их и резервное восстановление после изучения архива.
